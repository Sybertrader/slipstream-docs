Slipstream

Release Risk & Dependency Radar

Runs on Atlassian · Zero External Egress

The release date, before the status chase starts.

TPMs and release managers spend the week collecting the same update from spreadsheets and from four different Jira boards. Slipstream replaces that chase with one early-warning view that runs 100% on Atlassian.

  • The pain. The blocker that moves a date is rarely on the board you are looking at. It sits in another project, often only as a comment or a pull request name, and it shows up in the Monday meeting.
  • The radar. Slipstream reads the Jira work you already have and catches those unlinked cross-project blockers before they blow the date. It also reads the Blocks links your teams did keep.
  • The forecast. For each Fix Version with a release date, leaders see the chance of landing it, the longest chain of work, and what changes if one item slips. A version with no date is marked No date, not healthy.
  • The ROI. Cross-project release forecasting without forcing a $10-plus-per-seat Jira Premium upgrade across the company. Paid is $4.00 per user per month, or $40 per user per year. Jira data does not leave Atlassian.

2-minute quick start

The first page opens with no CSV, no spreadsheet, and no setup wizard.

01

Install

A Jira admin installs Slipstream from the Atlassian Marketplace. Atlassian is the merchant of record. After the 30-day Evaluation, Paid is $4.00 per user per month, or $40 per user per year.

02

Use a Fix Version

Put the release issues on a Fix Version and set its release date. That date is what the forecast is judged against. Issues without a version still appear on the portfolio view.

03

Run the first scan

Open Slipstream from the Jira Apps menu or the project sidebar and choose Run scan. The page updates when the scan finishes. No spreadsheet and no setup form.

04

Read the gate

The header shows On track, Watch, Hold, or No date, together with the chance of hitting the date and the length of the longest chain. The same warning appears on the Jira issue, so the engineer in the ticket sees it too.

Reading the Release Radar

On track

The screen shows GO. The release has a date, the chance of hitting it is 80% or better, nothing is stuck in a loop, and no open item is in the high-risk band.

Watch

The screen shows CONDITIONAL. The chance of hitting the date is from 50% up to 80%, or an open item is high risk. High risk starts at a score of 150. Critical starts at 250.

Hold

The screen shows HOLD. Work is still looping on itself, or the chance of hitting the date is below 50%.

No date

The screen shows NO DATE. A Fix Version has no release date, so Slipstream will not call the release healthy. Set the date to get a delivery chance.

Release forecasts

Each card is one Fix Version. The project key stays in the title, so two versions with the same name stay distinct, for example BILL · Slipstream Sandbox Train. The card shows the target date, how long the work is expected to take, the chance of hitting the date, and the projected finish. A missing date does not show a percentage.

What counts as a blocker

An item with no slack is on the longest chain. Slipstream also shows how much room the other items have. It treats these signals as dependencies:

  • A Blocks link — treated as certain
  • A parent or child epic that crosses projects — strong
  • A branch, pull request, or commit name written in a comment or description — the implicit case leaders usually miss
  • A plain issue key written in the text — weaker, and shown as such
  • The same Fix Version name in two projects — a release anchor, not a hand-drawn link

If work loops back on itself, Slipstream breaks the weakest link, shows which issues were in the loop, and does not pretend the loop is a schedule.

When an item has no story points, no time estimate, and no dates, Slipstream uses a plain default for that issue type and says so. A release made mostly of defaults is not called on track.

Why an item is a release risk

Each open item gets one risk score from three questions: how badly it can move the release, how likely that is, and how easy it is to miss. Finished items drop off the list.

What raises the score

Impact rises when the item sits on the longest chain or blocks work in another project. Likelihood rises when nobody owns it or it has already rolled a sprint. It is easier to miss when the only evidence is a comment, or when nobody estimated it. The page shows the three parts next to the score.

Inside the Jira ticket

Open any issue and read the Slipstream panel. It shows whether the item is on the longest chain, what is blocking it, what it blocks, and the short brief. Names and email addresses are not shown.

Ask what happens if it slips

A question, not a new plan

Add delay, remove a dependency, or move the release date. Slipstream answers from the scan already on the page. It does not change Jira and it does not save a second plan.

A note for the release review

Copy Release Brief produces a short note: the call, the chance of hitting the date, the longest chain, and the top risks. It leaves out account ids and email addresses, so it can go into the review.
