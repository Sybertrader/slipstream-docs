Technical guide

How Slipstream reads a release.

Graph traversal, critical-path maths, PERT confidence, and FMEA scores run in deterministic TypeScript. The model never computes the graph, the path, the confidence, or the RPN. On Paid and Evaluation it writes a short brief after those scores exist. Free and expired installs make zero model calls.

Setup

Install, open Slipstream, run a scan. No CSV, token, or setup form. For the security review, start with the scope list.

  1. Install from the Atlassian Marketplace. A Jira admin installs Slipstream. Atlassian is the merchant of record. After the 30-day Evaluation, Paid is $4.00 per user per month, or $40 per user per year. Request early access until the listing link is published here.
  2. Put the release issues on a Fix Version with a release date. That date is what the forecast is judged against. Issues without a version still appear on the Slipstream global and project pages. A Fix Version with no date leaves confidence empty.
  3. Open Slipstream and run a scan. Use the global page from Apps, or the project page. Scans run asynchronously and can take a few minutes on a large site, up to 900 seconds. The page updates when the scan finishes.
  4. Read the gate. The page shows GO, CONDITIONAL, HOLD, or NO DATE, together with the chance of hitting the date and the length of the longest chain.

Release gates

The call is chosen in this order. A missing number is never treated as a healthy release.

HOLDAny unresolved cycle, or confidence below 50%.
NO DATEConfidence is empty, or an undated Fix Version would otherwise be GO.
CONDITIONALConfidence is from 50% up to but not including 80%, or any open high-RPN item, and nothing has forced HOLD.
GOConfidence is at least 80%, there is no cycle, no open high-RPN item, and no undated Fix Version.

Readiness

Readiness starts at 100 and stays between 0 and 100.

  • −40 for any unresolved cycle
  • −30 if confidence is below 50%
  • −15 if confidence is from 50% up to but not including 80%
  • −15 for a missing date or confidence
  • −10 per high-RPN issue, up to −30

How each call arises

  • HOLD. The scan still contains an unresolved cycle, or confidence is 40%. Readiness loses 40 for the cycle, or 30 for confidence below 50%.
  • NO DATE. Confidence is empty because the Fix Version has no release date, and there is no cycle and no open high-RPN item. That release would otherwise be GO. Readiness loses 15.
  • CONDITIONAL. Confidence is 65%, with no cycle and no open high-RPN item. Or confidence is 90% and one open item is RPN 630. An undated Fix Version that also has an open high-RPN item is CONDITIONAL, not NO DATE.
  • GO. Confidence is at least 80%, there is no cycle, no open high-RPN item, and every watched Fix Version has a date. Readiness stays 100.

High starts at 150. Critical starts at 250. Both count as high-RPN. If the Fix Version has no date, confidence is left empty. It is not shown as 0% or 100%. The brief is shown on the Slipstream page and in the issue panel. v1.0 does not post a Jira comment and does not publish a Confluence page.

What counts as a blocker

An edge means the source finishes before the target starts. Only issue keys inside the scan become edges.

Key-like strings with the prefixes UTF, HTTP, HTTPS, SHA, CVE, or ISO are rejected. Examples include UTF-8, HTTP-500, SHA-256, and CVE-2026-1234.

Cycles are found with Tarjan’s algorithm. The lowest-confidence edge in the cycle is removed. Issues in the cycle get a cycle anomaly and Detection 10.

What Slipstream does not read: repositories, the Jira development panel (/rest/dev-status), source code, and Confluence.

When story points, the original estimate, the remaining estimate, and the start-to-due window are all missing, Slipstream uses the issue-type default and records DEFAULT_FALLBACK.

PERT and standard deviation

A working day is 8 hours. Done work is 0 days. The first signal found wins, in this order: story points counted as days, the original estimate, the remaining estimate, the start-to-due window, then the issue-type default. Defaults are Epic 15, Story 5, Bug 3, Task 3, Sub-task 1, and 5 for any other type.

  • Most likely, M, is that working-day duration.
  • Optimistic O = 0.8 × M.
  • Pessimistic P = M × (1.5 + 0.25 × risk-word hits). Risk words in the text include blocked, delay, risk, waiting, overdue, and slip.

Expected duration and variance for one item:

E = (O + 4M + P) / 6

variance = ((P − O) / 6)²

Variances add along the critical path. The standard deviation is the square root of that sum. Confidence against a target date uses the standard normal distribution, with the Abramowitz–Stegun approximation:

z = (T − E) / σ

The chance of finishing by T is the normal cumulative probability of z. A target one standard deviation after the expected path is about 84%. The expected path itself is 50%. Two standard deviations earlier is about 2.3%. Projected finish is today plus the critical-path duration in working days. If the Fix Version has no release date, confidence and z are left empty. They are not shown as 0%, and they are not shown as 100%.

FMEA formulas

Each open item gets one Risk Priority Number. Each factor is an integer from 1 to 10, so the open range is 1 to 1,000. Done items score 0.

RPN = S × O × D

Severity

Starts at 1. Add 4 when the item is on the critical path or its total float is zero. Add 3 when 5 or more issues sit downstream. Add 2 when those issues span 2 or more projects. Cap at 10.

Occurrence

Starts at 1. Add 2 for each sprint carry-over. Add 1 for every 4 stale days. Add 1 when variance is at least 1 day squared. Cap at 10.

Detection

Starts at 2. A broken cycle sets detection to 10. Otherwise add 3 for a cross-project link, 2 if every incoming edge is implicit, 2 if the item is unassigned, and 1 for a default estimate. Cap at 10.

Critical. A critical, cross-project, unassigned item with 2 sprint carry-overs, 8 stale days, implicit-only edges, and 5 downstream issues across 2 projects scores S10 × O7 × D9 = RPN 630, Critical.

Inside the Jira issue

The issue panel is titled Slipstream. On Free, and on an expired Evaluation, it shows a blocker warning. On Paid and Evaluation it shows the same warning, plus the stored brief when a model ran. The only person identifier stored is the assignee’s Atlassian account id. Names and email addresses are not stored.

What-if

Delay one item, or several items on Paid and Evaluation, or remove a dependency. Slipstream reruns cycle breaking, the critical path, PERT, and FMEA on a copy of the loaded snapshot. The answer stays in memory. It never writes to Forge SQL or to Jira.
